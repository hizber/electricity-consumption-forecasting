# Shared next-hour forecasting features

Run `python3 generate_features.py --output-dir OUTPUT_DIRECTORY --weather-latency-hours 1` from this directory. Python 3.10+ and an IANA timezone database are required for the complete pipeline and tests. The output directory must not already exist. The default input is the supplied course CSV. `--input PATH` selects another file with the same schema.

The generator produces `features.csv` and `labels.csv`, joined by `target_end_utc`. `origin_utc` and `target_end_utc` are metadata, not predictors. Select predictor columns explicitly. Labels contain actual target consumption and must remain separate from model inputs. Split by target time and fit scalers, imputers, feature selection and hyperparameters using training folds only. Earlier readings can provide context to a later forecast when available at its origin.

At the end of hour `t`, the meter reading for that hour is available according to the project owner, and the model predicts the hour ending at `t+1`. `load_lag_001` is `y[t]`, `load_lag_024` is `y[t−23]` and `load_lag_168` is `y[t−167]`. Select the first 24, 72 or 168 lag columns for a model's history, ordering them oldest to newest when building a sequence. All output rows require 168 complete history readings, ensuring the same origins across these configurations. The summaries are calculated over the completed 3, 6, 24 or 168 readings ending at the origin. Standard deviation is population standard deviation. Change is newest minus oldest within each window, spanning one fewer elapsed hour than the window size.

Hour, weekday, weekend, day of year and Finnish public holiday are calculated for the target interval's **end** in `Europe/Helsinki`. Lags are elapsed UTC hours, including across daylight-saving transitions. The holiday indicator includes statutory public holidays, including Easter and midsummer dates. It does not encode holiday eves or school holidays.

## Weather availability

The assignment CSV already includes hourly FMI station observations. Its source script identifies Jyväskylä airport station 101339, with temperature, humidity and wind. These historical observations are the weather source for this experiment. FMI says its past-weather web display usually updates every 10 minutes, while hourly observations summarize the preceding hour. This describes the current service and does not establish when each 2016–2022 historical hourly value was published or revised. [FMI weather services](https://en.ilmatieteenlaitos.fi/weather-services-on-the-internet), [FMI observation guidance](https://en.ilmatieteenlaitos.fi/guidance-to-observations).

The example assumes a one-hour publication delay. For target `t+1`, the newest weather observation used ends at `t−1`. This is a provisional experiment assumption, not proof that all historical observations were available by the origin. Test a longer delay if needed and record the chosen assumption with results. Without `--weather-latency-hours`, weather is omitted. Weather values are never taken from the target hour. Missing observations remain empty and latest-value missingness indicators are provided. Rolling temperature summaries require a complete window. Do not fill missing values using future data. Learn any imputation or scaling parameters only on the fitting fold. The 2016 weather provenance needs confirmation because the PDF states weather begins in 2017.

The features include latest available temperature, humidity and wind, temperature means and changes over 3, 6, 24 and 168 hours, and `max(0, 15 − temperature)` as a trial heating indicator. The 15 °C threshold is a hypothesis. Archived weather forecasts and solar data are not included because suitable historical forecast vintages and coverage have not been verified.

## Tests

Run `python3 -m unittest -v test_generate_features`. Tests cover lag alignment, future-data perturbation, delayed and missing weather, Finnish holiday dates and the repeated Helsinki hour at the daylight-saving transition. The generator requires consecutive hourly timestamps and fails on gaps or duplicates. It skips rows with missing consumption in the target or required history. It performs no fitted preprocessing.

## Rebuild both prepared datasets

Run `python3 build_datasets.py --output-dir NEW_DIRECTORY` from this folder. The output directory must not exist. Use `--input PATH` to specify a different source CSV. To create a separate conditional weather build, add `--weather-latency-hours 1` and use an output directory under `generated_weather_1h/`. The command produces `hourly/` and `daily/`, each with `fit`, `validation`, `test`, `evaluation_1`, `evaluation_2` and `evaluation_3` subfolders. Each contains separate `features.csv` and `labels.csv`. Join on `origin_utc` and `target_end_utc`, and preserve row order. These two timestamps are metadata. The root `manifest.json` records source, script and output hashes, predictor columns, split boundaries, row counts and assumptions. It does not fit an imputer, scaler or model. The prepared copy is in [prepared_no_weather](prepared_no_weather/manifest.json).

The hourly task predicts the hour ending one hour after the origin. The daily task issues one forecast at 00:00 UTC for the next 24 elapsed hours. Its long-form table has 24 rows per origin, one for each `horizon_hours`. Every row shares the same 168 completed consumption readings at that origin. Target-specific previous-day/week lag and calendar features use only values available at the common origin. The 24 values can be grouped by origin to create a vector output or predicted as separate horizon rows. These are 24 hourly consumption values, and their sum gives a 24-hour total. This schedule follows the existing baseline and is a provisional UTC schedule, not a Helsinki calendar-day schedule.

The development fit period ends 30 September 2019, followed by the validation year. Test and evaluation periods follow the assignment. Target-end timestamps are assigned using UTC boundaries provisionally. All 24 target hours must belong to one split, so a profile crossing a boundary is excluded. The final source day is incomplete and cannot provide a complete daily profile. Counts are in the manifest. Historical consumption from before a split may be used as input where it was available at the forecast origin. Later labels are never used for fitting or for choosing features. Fix model settings using fit and validation, then freeze them before evaluating the held-out periods. Apply fitted preprocessing using only the fitting fold, and rebuild it separately for each cross-validation fold.

The prepared copy excludes weather because the publication time and revision vintage of historical observations are not established. `generated_weather_1h` is a separate exploratory dataset whose weather timing is conditional on a one-hour delay assumption. Its results cannot establish a guaranteed leakage-free operational forecast. No features are selected using test or evaluation labels. The project owner confirmed that the meter reading is available at the origin.

For a 24- or 72-hour input-window comparison, remove longer lag and rolling features as well if the aim is to restrict the model's entire history. The shared 168-hour aggregates otherwise still expose longer history.

Run `python3 -m unittest -v test_generate_features test_generate_daily_features` to verify both horizon builders.
